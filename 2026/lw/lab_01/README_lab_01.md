## 5. Минимальные теоретические сведения

RDD — распределённая неизменяемая коллекция; DataFrame — распределённая таблица со схемой,
для которой Spark строит оптимизированный logical и physical plan.

Вычисления **ленивые**: `select`, `filter`, `groupBy`, `map` формируют lineage и ничего не
считают; работу запускает только **действие** — `count`, `show`, `collect`, `write`.

При агрегации по ключу записи с одинаковым ключом должны оказаться в одной partition, поэтому
выполняется их перераспределение между узлами. Эта стадия называется **shuffle**; она связана
с сетевым и дисковым вводом-выводом и образует границу stage.

MapReduce-представление агрегации:

```
map:     (k₁, v₁) → [(k₂, v₂)]
reduce:  (k₂, [v₂]) → v₃
```

Среднеквадратичное ускорение, которое требуется рассчитать в части 2:

```
RMS = sqrt( mean( ax² + ay² + az² ) )
```

то есть сначала усреднение суммы квадратов, затем извлечение корня.

## 6. Ход работы

### Часть 1. MapReduce своими руками

1. Открыть `lab_01_student.ipynb` в Google Colab, выполнить установочную ячейку и создать
   `SparkSession` в режиме `local[*]`.
2. Сгенерировать журнал диагностических сообщений робота на 20 000 строк.
3. Реализовать функцию `mapper(path)` — вернуть список пар `(слово, 1)` по тексту сообщений.
4. Реализовать функцию `partitioner(pairs)` — сгруппировать пары по ключу
   (подсказка: `collections.defaultdict`).
5. Реализовать функцию `reducer(item)` — свернуть `(слово, [1, 1, …])` в `(слово, количество)`;
   вывести пять самых частых слов.
6. Повторить подсчёт средствами RDD: `textFile → flatMap → map → reduceByKey → takeOrdered`;
   убедиться, что результат совпал с чистым Python.
7. Письменно ответить, какая операция цепочки создаёт shuffle и чем `reduceByKey` лучше
   связки `groupByKey().mapValues(sum)`.

### Часть 2. DataFrame API

8. Сгенерировать журнал телеметрии на 500 000 записей (8 роботов, показания IMU по трём осям,
   температура двигателя, напряжение батареи); зафиксировать число partition.
9. Закрепить датасет в памяти уровнем `MEMORY_AND_DISK` и материализовать его действием `count()`.
10. Построить агрегацию по `robot_id`: число записей, средняя и максимальная температура
    двигателя, среднее напряжение, среднеквадратичное ускорение.
11. Через `rdd.mapPartitionsWithIndex` проверить фактическое распределение записей по partition
    и письменно объяснить полученную картину.

### Часть 3. Spark SQL

12. Зарегистрировать DataFrame как временное представление `robot_logs`.
13. Написать SQL-запрос с `GROUP BY`, `HAVING MAX(motor_temp) > 50` и сортировкой по убыванию
    максимальной температуры.
14. Соединить результаты DataFrame API и Spark SQL по `robot_id` и убедиться, что средние
    температуры совпадают с точностью до округления.

### Часть 4. Physical plan и партиционирование

15. Выполнить `summary.explain(mode="formatted")`, найти операторы `Exchange` и `HashAggregate`,
    письменно объяснить назначение каждого и природу двухфазной агрегации.
16. Измерить время агрегации при `spark.sql.shuffle.partitions`, равном 2, 4, 8 и 64.
    На время эксперимента отключить Adaptive Query Execution
    (`spark.sql.adaptive.enabled = "false"`), иначе оптимизатор сам объединит лишние partition
    и влияние параметра будет незаметно. Каждое измерение повторить трижды, взять минимум.
17. Письменно интерпретировать результаты: какое число partition оказалось лучшим, что произойдёт
    при значении по умолчанию (200) и как число partition связано с `sc.defaultParallelism`.

* Ноутбук с ошибками выполнения или ячейками, выполненными не по порядку.
* Текстовые ответы, оставленные в виде `TODO`, или ответы из одного предложения.
* `TEACH CARD` с общими формулировками, без измеримого результата и критерия успеха.
* Замер времени без вызова действия — из-за ленивости он покажет околонулевые значения.

Абсолютные значения времени в части 4 зависят от runtime и у всех будут разными: оценивается
корректность методики измерения и интерпретация, а не совпадение цифр.
