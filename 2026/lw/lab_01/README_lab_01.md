# Лабораторная работа № 1 — обновлённая версия

**Дисциплина:** «Методы обработки больших данных»
**Тема:** Распределённая пакетная обработка логов робототехнических комплексов в Apache Spark
**Этап конвейера:** `Collect → Store → Process`

## Состав комплекта

| Файл | Назначение |
|---|---|
| `lab_01_student.ipynb` | Вариант для студента: задания с заготовками `TODO`, ячейки очищены от выводов |
| `lab_01_teacher_solution.ipynb` | Вариант преподавателя: полное решение, все ячейки выполнены, выводы сохранены |

Оба ноутбука рассчитаны на Google Colab: PySpark 4.2.0, режим `local[*]`, внешний датасет не требуется.
Эталонный прогон выполнен на PySpark 4.2.0 / OpenJDK 21 — все 13 автопроверок проходят.

## Что изменено относительно `lab_01_spark_batch.md`

**Было:** один сплошной блок кода на 60 строк и семь пунктов «хода работы». Студент запускает
готовый код и получает результат, не написав ни строки. Проверить, что именно он понял,
невозможно.

**Стало:** 13 упражнений с автопроверкой, разбитых на пять частей по критериям оценивания.

### 1. Добавлена вводная часть «MapReduce своими руками»

По мотивам ноутбуков `04-WordCount` и `05-MapReduce` из репозитория `pnavaro/big-data`.
Студент последовательно пишет `mapper`, `partitioner` и `reducer` на чистом Python над журналом
диагностических сообщений робота, затем повторяет тот же расчёт на RDD API
(`flatMap → map → reduceByKey → takeOrdered`) и сверяет результаты.

Смысл: прежде чем запускать распределённый движок, увидеть, что Spark выполняет ровно три шага,
которые студент только что написал руками. Дополнительно вводится различие
`reduceByKey` vs `groupByKey` — типовой вопрос на понимание shuffle.

### 2. Каждое задание снабжено автопроверкой

Вместо двух `assert` в конце — 13 проверок по ходу работы плюс сводная таблица самопроверки.
Студент видит, засчитано ли задание, до сдачи. Проверки содержательные, а не формальные:
например, RMS проверяется на попадание в диапазон 9,0–11,0, а результат Spark сверяется
с результатом чистого Python.

### 3. Исправлена неоднозначность сортировки

В подсчёте частот слов встречаются одинаковые значения (`motor`, `controller`, `timeout` —
по 4951). Сортировка только по частоте даёт разный порядок в Python и в Spark, и наивная
проверка `assert` падает. В ключ сортировки добавлено само слово: `key=lambda kv: (-kv[1], kv[0])`.

### 4. Эксперимент с партиционированием сделан корректным

В исходной версии предлагалось сравнить время при 2, 4 и 8 partition. На практике измерение
ничего не показывает: **Adaptive Query Execution сам объединяет лишние partition после shuffle**,
и разница исчезает. В новой версии AQE на время эксперимента отключается
(`spark.sql.adaptive.enabled = false`), добавлено значение 64 и трёхкратный повтор с взятием
минимума. В ответе преподавателя честно оговорено, что на 500 тыс. записей разброс сопоставим
с шумом измерения и эффект проявляется на данных на два порядка больших.

### 5. Добавлено упражнение на перекос данных

Проверка распределения записей по partition даёт неожиданный результат: при `repartition(8, "robot_id")`
и восьми роботах две partition оказываются пустыми, а одна получает втрое больше записей
(62500 / 62500 / 62500 / 0 / 0 / 187500 / 62500 / 62500). Это происходит из-за хэширования ключа
и является наглядной иллюстрацией data skew — понятия, которое иначе остаётся абстракцией.

### 6. Добавлена сверка DataFrame API и Spark SQL

Отдельное упражнение: соединить результаты двух API по `robot_id` и убедиться, что средние
температуры совпадают с точностью до округления. Показывает, что оба API проходят через один
оптимизатор Catalyst.

### 7. Расширено задание по physical plan

Вместо «найдите Exchange» — развёрнутый разбор двухфазной агрегации: почему `HashAggregate`
встречается дважды, что делает `Exchange hashpartitioning`, откуда берётся
`Exchange rangepartitioning` для `ORDER BY` и что означает `AdaptiveSparkPlan` в корне плана.

### 8. Технические правки

* добавлен `spark.ui.showConsoleProgress = false` — прогресс-бары Spark засоряли вывод ячеек;
* bash-магии (`!head`, `!wc`) заменены на переносимый Python;
* генератор журнала детерминирован (`random.seed(42)`) — результаты воспроизводимы у всех студентов;
* явно указано, где нужен `action`, иначе из-за ленивости замер времени покажет ноль.

## Порядок проверки работы

1. Открыть студенческий ноутбук, убедиться, что все ячейки выполнены сверху вниз без ошибок.
2. Посмотреть сводную таблицу самопроверки в конце: должно быть «Выполнено: 13 из 13».
3. Прочитать текстовые ответы `ANSWER_1_5`, `ANSWER_2_3`, `ANSWER_4_1`, `ANSWER_4_3` — они
   не проверяются автоматически и составляют основную содержательную часть оценки.
4. Оценить TEACH CARD: конкретность формулировок, наличие измеримого результата, критерия успеха
   и честно названных ограничений.

Абсолютные значения времени в части 4 у студентов будут отличаться от эталонных — оценивается
корректность методики измерения и интерпретация, а не совпадение цифр.
