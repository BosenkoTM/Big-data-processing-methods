## Цель

Построить потоковую обработку сенсорных событий робота с event time, скользящими окнами и
watermark; измерить, чем оплачивается полнота данных; объяснить полученный инженерный
результат на языке, пригодном для школьника.

## Задачи

1. Сформировать поток телеметрии нескольких роботов с контролируемой долей опоздавших событий.
2. Рассчитать оконные агрегаты по event time и получить корректный снимок результата.
3. Измерить влияние watermark на полноту данных и объём состояния.
4. Объяснить, что меняется при переходе на Kafka source.
5. Разработать педагогическую адаптацию результата: `TEACH CARD` и фрагмент занятия.

## Связь с лекцией

| Понятие лекции | Где проверяется в работе |
|---|---|
| модель потока, $\lambda$, $\mu$, $\rho$ | метрики micro-batch: пропускная способность и длительность батча (часть 3) |
| event time против processing time | колонка `event_time` и искусственно опоздавшие события (часть 1) |
| скользящее окно, $M \approx W/S$ | проверка фактической кратности окон (часть 3) |
| watermark, $\mathrm{WM} = \max(t_{event}) - \Delta$ | эксперимент с двумя значениями $\Delta$ (часть 3) |
| состояние оператора | `numRowsTotal`, `memoryUsedBytes` из метрик прогресса (часть 3) |
| Kafka: topic, partition, offset, key | разбор переноса кода (часть 4) |
| педагогический мост | `TEACH CARD` и фрагмент занятия (часть 5) |

Kafka, KRaft и Flink в обязательной части не выполняются: они разбираются на лекции и выносятся
на защиту в виде вопросов.

## Теоретический минимум

**Поток как неограниченная таблица.** Запрос пишется как для обычного DataFrame, а движок
пересчитывает результат микропакетами. Для устойчивости нужно $\lambda < \mu$, где
$\rho = \lambda / \mu$ — коэффициент загрузки.

**Два времени.** `event_time` — момент измерения (проставляет устройство), `processing_time` —
момент обработки. Задержка доставки $L = t_{processing} - t_{event}$. Ось анализа сенсорных
данных — event time: только тогда повторный прогон над теми же данными даёт тот же результат.

**Скользящее окно** длиной $W$ с шагом $S$:

$$W_k = [t_0 + kS,\; t_0 + kS + W),$$

одно событие попадает примерно в $M \approx \lceil W/S \rceil$ окон.

**Watermark:**

$$\mathrm{WM}(t) = \max(t_{event}) - \Delta.$$

Окна, оставшиеся позади watermark, финализируются, их состояние удаляется, а опоздавшие
события для них отбрасываются. Spark считает их метрикой `numRowsDroppedByWatermark`.

| Большая $\Delta$ | Малая $\Delta$ |
|---|---|
| больше опоздавших событий учтено | меньше задержка финализации |
| больше состояния в памяти | меньше состояния |
| позже готов итог | выше риск потерять данные |

Этот компромисс и измеряется в части 3 — числами, а не словами.

## Два подводных камня (разобраны в эталоне)

1. **`processAllAvailable()` нельзя применять к источнику `rate`.** Он порождает данные
   непрерывно, поэтому «все доступные данные» не заканчиваются, и вызов может заблокировать
   ячейку. Останавливайте поток по таймеру.
2. **`memory`-приёмник в режиме `update` хранит историю обновлений.** Одна пара «окно — робот»
   попадает в таблицу после каждого micro-batch, в котором изменилась. В эталонном прогоне это
   134 строки при 29 реальных окнах. Число строк такой таблицы — не число окон.

## Часть 5. Педагогическая часть

Инженерный результат работы сводится к трём утверждениям, которые можно объяснить школьнику
без терминов движка:

1. **У события есть два времени** — когда оно случилось и когда о нём узнали; считать надо по
   первому.
2. **Ждать опоздавших — значит занимать память**: чем дольше система ждёт, тем больше хранит и
   тем позже выдаёт итог.
3. **Скользящее окно считает одно событие несколько раз** — ровно $W/S$ раз.

### `TEACH CARD` (1,5 балла)

| Поле | Что указать |
|---|---|
| Название учебного проекта | рабочее название для школьников |
| Целевая аудитория | задана вариантом |
| Исследовательский вопрос | вопрос, на который отвечает ученик, без терминов Spark |
| Источник данных | что служит потоком: карточки, таблица, датчик смартфона, микроконтроллер |
| Инженерная концепция, сохраняемая без упрощения | что именно переносится из лабораторной в школу |
| Что упрощается | от чего отказываемся и почему это не ломает суть |
| Алгоритм действий обучающегося | 4–6 шагов |
| Измеримый результат / метрика | что считают ученики |
| Критерий успешного выполнения | когда задание засчитано |
| Вариант усложнения для НТО / хакатона | развитие для сильной группы |
| Риски и ограничения | где модель расходится с реальностью |

### Фрагмент занятия (1,5 балла)

Описание на 15–20 минут по одному из трёх выводов. Обязательны: действия учеников, **два
числа своего прогона**, ключевой вопрос и способ проверки понимания с указанием типичного
заблуждения, которое он ловит.

Не засчитывается: пересказ лекции без действий учеников; чужие числа; объяснение термина
«watermark» словом «watermark».

## Адаптация к Kafka (разбирается, не выполняется)

```python
raw = (
    spark.readStream
    .format("kafka")
    .option("kafka.bootstrap.servers", "broker:9092")
    .option("subscribe", "robot.telemetry")
    .option("startingOffsets", "latest")
    .option("maxOffsetsPerTrigger", 5000)
    .load()
)

schema = "robot_id STRING, event_time TIMESTAMP, motor_temp DOUBLE, vibration DOUBLE"
telemetry = (
    raw.select(F.from_json(F.col("value").cast("string"), schema).alias("e")).select("e.*")
)
```

Меняются источник, разбор `value` и позиционирование по offset; оконная логика и watermark
остаются прежними. Ключ `key = robot_id` обеспечивает порядок событий одного робота внутри
partition, параллелизм ограничен числом partition, а `checkpointLocation` становится
обязательным: в нём хранятся offset источника и состояние операторов.
